- Brief dive into magic with managers:

  - Usually, memory management in C is _extremely_ error prone.
    So is error handling!
    - Super repetitive, and it's easy to miss something.
    - malloc with error checking is messy, but there's
      a slight bonus for freeing: null pointers are OK!
    - This may seem unnecessary in something like C++,
      but it would be _painful_ to write out the minimum
      destructors manually.
      - In other words, if we create objects A, B, and C,
        we would need to do error handling at _each_ object.
        - If A fails to be created, then abort.
        - If B fails to be created, destroy A _then_ abort.
        - If C fails to be created, destroy B, _then_ destroy A, _then_ abort.
      - This has a nasty triangle pattern that is horrendous
        to write!
  - What if we could specify create/destroy _once_?
    - It would be much easier to audit and debug.
      More explicit than throwing in a C++ constructor.
      It's a similar idea to defer, where we
      see creation _and_ destruction in the same place.
    - Maybe we could make pairs of these!
      It would be nice to declare what we want,
      and not worry about writing the calls by hand.
  - Here's the magic: this can be done with function pointers!

    - Create an array of _managers_, which are
      constructor/destructor pairs.
      (As a shorthand, I've written this as new/del).
      - To simplify type handling, assume everything
        uses an input struct.
      - You can think of these as objects,
        but without all the methods. We are _just_
        creating and destroying them. No more, no less.
    - We then operate on the stack (just like RAII,
      but explicit):
      - Push each manager by calling new, with _one_ line
        for error handling (in the main loop).
      - Pop each manager with del.
    - This now gives us a nice declarative interface
      for managers!
      - We _do_ need to check for the size of the array,
        but this is easy to do. We can even
        add static asserts for extra assurances.
    - Best of all, some compilers (i.e., clang in -O2) can inline
      all of this!

      - In other words, the compiler writes out
        what we _would_ have done by hand!
        This is exactly why compilers are so useful
        (as a small example)!
      - GCC can do this with arrays of _simple_ types,
        but not usually with function pointers.
        I will have to investigate what optimization
        pass clang has. Maybe there's a way to
        incorporate the same optimization in other compilers?
        - Of course, you _could_ use a macro,
          but it's still difficult to _store_
          the constructor and destructor in one place!
          You likely would end up some list of these pairs,
          which is basically this approach (but
          more error-prone).
      - There is one major limitation: clang can't always
        (maybe never?) inline arrays of function pointers
        passed into other functions.

        - This would be nice for, say, storing
          both loops.
        - The workaround for this is to make the managers
          global, static, and _constant_. A bit harder
          to tell control flow, but not terrible.
        - Personally, I like seeing the loops - might
          as well get a good feel for main!
        - However, if we use this same idiom again
          in the main event loop, we might have to
          reconsider how this works. (Separate files
          aren't a bad idea.)

      - In any case, this isn't super important,
        performance wise. Debugging wise,
        it is important. We don't want to see
        all these stack addresses when calling functions!
        Having them inlined is much better (and is one
        case where loop unrolling _is_ better, overall).

    - Main takeaway: I'm excited to use this as a common
      idiom in the code base! Actually a place where C
      type checking is alright. (Still need to avoid
      most void pointers...)

## Questions

- What types of games are "casual games"?
  - I don't want to include anything
    with lots of moving parts. Platformers
    are _definitely_ excluded.
    But minigames can have a fast pace,
    which makes things difficult...
  - My aim is to limit the scope enough
    so this project doesn't explode too much.
    - For something like tower defense,
      I would rather make a new project.
      (It would be nice to base it off of
      a base template, with the same idioms!)
- Can we force clang to inline our special functions?
  - For init/quit, seems completely unnecessary.
    But for the main event loop, this could be useful.
  - At the same time, the overhead may be so small
    that it doesn't affect _speed_. Code size
    and energy may be other things (but, those too
    are probably dwarfed by the rest of the program)
- Good documentation generators?
  - Not sure the best place to start.
    - Definitely needs to generate HTML,
      and be easy to read in C. Also,
      plenty of links!
    - Something like docs in rust.
    - Preferably not too big of a dependency?
      I'm only using CMake because it's industry
      standard, works well with SDL, and _can_
      do cross compilation. I don't want something
      larger, like React.
  - This could also be incorporated
    with future plans to statically analyze
    the code base for common errors.
    (This would be really nice to make sure functions
    behave _exactly_ in one way!)
    - I have some ideas with pycparser and
      a custom lsp,
      but that's probably a few dev logs down the line.
