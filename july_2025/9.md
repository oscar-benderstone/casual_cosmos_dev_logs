### Generic Arrays (Almost)

I settled on a solution
to the generic arrays problem:
creating void pointers and
carefully doing typecasts.

- The easiest solution (1)
would be to use macros.
*However*, my goal
is to make nearly all
of the application
macro free.
  - Ultimately, I think this will
  be helpful for everyone!
  And it's possible within
  my use of C23!
  - Sure, some things will
  get repeated, but I think
  that's a good thing.
  We *don't* want to
  put complicated
  control flow
  in a macro!
  - In any case,
  macros aren't going
  to work.
- Another easy idea (2):
create separate functions
for each type I want to use.
  - Extremely repetitive
  and tedious!
  Things can go wrong
  with just one offs
  in the start or
  end index.
  (Think about
  a missing new or del...).
  - It's hard to tell
  that they're *all*
  basically the same thing.
  We iterate over an array,
  with a custom callback
  each element.
- My solution (3):
create a *single*
function to handle
iteration via void pointers.
  - Passing arrays is
  automatic, as any pointer
  type in C can be
  automatically converted
  to a void *.
  - However, the function
  type is more tricky,
  and is one strength
  of the second solution.
  There's no equivalent
  to `void *` conversion!
  We generally *have*
  to write out `void *(void)`.
  (And possibly
  `void (void*)`,
  though we could return
  a `nullptr` for that).
  - The cheap, but BAD
  solution, is to call
  the function as is.
  *Even if* the arguments
  are correct, this is
  undefined behavior!
    - *Maybe* clang
    won't have an issue.
    (When optimized,
    inlining seemed to
    "fix" the issue in
    the assembly).
    - This is still a BAD
    thing to do. Maybe
    clang will stop working
    with this!
    - I only want optimizations
    to work on *already correct*
    code, which includes
    my idiom (arrays of function pointers).
    - Not to say that the unoptimized
    version is necessarily *secure*;
    I could see a hacker trying to
    change a malicious function pointer
    (though we  could maybe block this
      with a `const` array or some stack validation.)
    But the functions *are* still
    called in the correct order
    (which is the crucial invariant!).
  - To me, the clearest way is
  to do the conversion *directly*.
  No wrappers, no macros.
    - Just wrap the desired callback
    in a `void *(void *)` function.
    This needs to be done each time,
    but it's more flexible.
      - For simplicity,
      I don't think I'll include
      methods like `get`
      or `assign`.
      Those would require
      type-casting *before*
      either operation
      (and would be *far* easier
      with the original array,
      before casting it to a `void *`).
      - What we *can*
      do generically
      is check if an item
      is a NULL pointer or not.
      That's all we need
      for the iteration methods!
      The callbacks handle the rest.
      - (Plus, this can be used to
      define `get` and `assign` when needed:
      just take a slice of the iterator
      and write the corresponding callback.)
    - We can even use Clang's
    Blocks from Objective-c
    to write these as a closure.
    - It does lock us into Clang
    (and blocks *should* be standardized
    as lambdas), but if my idiom
    already requires Clang,
    it's not a terrible idea.
    (Other languages, like Rust,
    *depend* on the LLVM codebase
    for their sole implementations.
    It's not a crazy idea!)
- Eventually, I'll make a static type checker
to enforce this pattern
(and reuse this code for the LSP).
  - If we restrict the format of the
  wrappers, it would be easy to
  statically analyze via
  Python bindings to `libclang`.

### ADoc (aka AsciiDoc)

I am migrating the docs
to AsciiDoc!

- I really don't like the name,
because it does have UTF-8 support
So I'm calling it ADoc.
(Kinda sounds neat!)
- Markdown is fine, but I would
like to have more control over
editing, and get into less ambiguity
overall.
  - Having worked on entangled,
  I kept asking myself
  about the non-standard
  inclusion of an attribute.
  AFAIK, there doesn't
  seem like a standardized
  way to handle these attributes!
    - And getting to more
    advanced HTML... I would
    rather use something like
    ADoc for that (and not
    get into inline HTML,
    that apparently can be
    lead to an exploit!)
  - Additionally, I saw that ADoc
  has a PEG parser (in a repo
  to develop a formal spec),
  which resonated with
  my mathematical side.
  (They used the word proofs!
  You don't see that with
  most markup languages...)
- However, this will be
a bigger commitment to
literate programming.
  - Entangled uses regular expressions
  specifically for Markdown.
  I was thinking about if I could
  do the same with ADoc,
  but it seems like there's a nicer
  way.
    - As ADoc is more standardized,
    the parser is more reliable!
    So we can do literate programming
    by using ADoctor (the main
    implementation)
    to query for all the code blocks.
    - Honestly, using the ADoctor
    API is easier than using a regex!
    (And more readable, though
    great labels were added to entangled).
      - I am adding Yet Another Programming Language,
      namely Ruby, but I think it's worth it.
      We'll see if how many the engine gets!
  - To make sure I get to work on the
  *game* (I haven't forgotten about that!),
  I think I will stick to the simplest solution:
  just tangle to a file!
    - No special weaving or macros.
    Just direct copy and paste!
    - I don't even *need*
    AsciiDoc for this
    (*looks at awk in the corner*),
    but honestly,
    it's more reliable and isn't
    that hard to do.
    - Stitching isn't that hard
    either, but does mean
    I will need to track comments.
    And I'm still trying to figure out
    how I want to structure the docs.
    - The only main thing I would miss
    are the database capabilities.
    But I've ran into issues
    with entangled before, and
    wouldn't mind having a simpler system
    (just run tangle/stitch manually,
    or *every* time the file is modified).
  - I'm sure I could do cool
  things with entangled's features,
  but that makes me think
  of more fundamental questions.
    - How do I want to organize
  project roadmaps?
    - How do I want to organize commits
  and project history?
